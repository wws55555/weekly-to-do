# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page Korean-language weekly to-do list ("위클리 플래너") with per-account private data — each person signs in with email/password and only ever sees their own lists, synced across whatever devices they log into. It's used purely as an Android app via a Capacitor shell — there is no web hosting/deployment target (Firebase Hosting was intentionally removed; `firebase.json` configures only `firestore.rules`, no `hosting`).

## Source of truth: `public/`

The whole app is a handful of plain files under `public/` — no bundler, no npm build step, no JSX precompilation anywhere. React, ReactDOM, and Babel Standalone come from CDN `<script>` tags in `index.html`; everything else is loaded as separate `<script>` tags in a fixed order (see `index.html`), sharing one global scope like any classic multi-script page (no ES modules, no `import`/`export`):

- `index.html` — just the `<head>`/CDN tags/script-loading skeleton; no app logic.
- `styles.css` — all CSS (page shell + the `.wk-*` design system).
- `dateUtils.js` — pure date/label helpers (`getMonday`, `addDays`, `toKey`, `formatMD`, `isSameDay`, `uid`, `DAY_LABELS*`). Plain JS, no Babel needed.
- `firestoreApi.js` — the *only* file that talks to Firebase. Exposes `WeeklyPlannerAPI` (`firebaseReady`, `watchAuthState`, `signUp`, `signIn`, `signOutUser`, `changePassword`, `watchWeek`, `updateWeek`, `fetchWeeksInRange`, `runCarryOverFromPrevWeek`, `moveTaskAcrossWeeks`, `watchMemos`, `createMemo`, `updateMemo`, `deleteMemo`) as plain functions; knows nothing about React. Does **not** sign anyone in automatically — it only reports auth state and exposes explicit sign-up/in/out calls.
- `useWeeklyTasks.js` — a custom hook holding all state, effects, and the carry-over decision logic, *plus* the auth state/actions (`authUser`, `authChecked`, `authError`, `authPending`, `signUp`, `signIn`, `signOut`, `changePassword`). Calls into `WeeklyPlannerAPI` for persistence, calls into `dateUtils.js` for date math, and returns a plain object of state + actions. Plain JS (hooks are just function calls; no JSX here), so no Babel needed either.
- `useMemos.js` — the memo pad's hook: takes `authUser` from `useWeeklyTasks()`, live-subscribes to the account's memos and returns `memos`, `memosLoading`, `memosConnectionOk`, `addMemo`, `editMemo`, `removeMemo`. Plain JS like `useWeeklyTasks.js` (and relies on its `useState`/`useEffect` destructure).
- `icons.jsx` — icon components, no logic.
- `CalendarGrid.jsx` — the month-grid date picker (Monday-first, today outlined, selected date filled, per-date task markers from the hook's `fetchCalendarMarks`). Shared by the header's 날짜 선택 modal and the edit-task modal's date field so both pickers look identical; owns only which month is shown and that month's markers.
- `AuthScreen.jsx` — the email/password sign-in/sign-up form, shown whenever there's no signed-in user. Owns only its own input state; calls the `onSignIn`/`onSignUp` props it's given.
- `ChangePasswordModal.jsx` — the change-password dialog (current / new / confirm), opened from the account (user icon) dropdown in the planner header next to 로그아웃. Owns only its own input state and validation; calls the `onSubmit` prop (the hook's `changePassword`, which re-authenticates with the current password before `updatePassword`, since Firebase requires a recent sign-in for that).
- `EditTaskModal.jsx` — the edit-task dialog (text + a date field that expands an inline `CalendarGrid`, 취소/저장), opened from a task's 수정 menu item. Owns only its own input state; calls `onSave(text, dateKey)` (`saveEdit` in `WeeklyPlanner.jsx`, which picks the `editTask` call shape).
- `MemoPad.jsx` — the 메모장 view (memo list, most recently edited first, plus a `MemoEditorModal` with a textarea and 취소/저장/삭제), shown instead of the planner panel when the header's mode switch is on 메모장. A memo is free text whose first line doubles as its list title.
- `WeeklyPlanner.jsx` — pure UI: calls `useWeeklyTasks()` and renders either `<AuthScreen>` (not signed in) or, signed in, the header with a 플래너/메모장 mode switch under the title (`mode` state, remembered per device in `localStorage` key `wkMode`) and then either the planner or `<MemoPad>` — no Firestore calls or carry-over logic live in it.

Because there's no module system, load order in `index.html` **is** the dependency graph — `dateUtils.js` → `firestoreApi.js` → `useWeeklyTasks.js` → `useMemos.js` → `icons.jsx` → `CalendarGrid.jsx` → `AuthScreen.jsx` → `ChangePasswordModal.jsx` → `EditTaskModal.jsx` → `MemoPad.jsx` → `WeeklyPlanner.jsx`. Get that order wrong and things fail with "X is not defined" at runtime, not a build error. For the same reason, don't add a second `const { useState, ... } = React` destructure in another file — it's already done once in `useWeeklyTasks.js`; a second top-level `const` with the same name in another classic script is a `SyntaxError` (they share one script-level scope). Reference `React.useX` directly instead if a component-level file needs a hook (see `WeeklyPlanner.jsx`'s/`AuthScreen.jsx`'s `React.useState`).

Everything here lives under `public/` (rather than the repo root) only because that's Capacitor's `webDir` (see `capacitor.config.json`) — the folder `npx cap sync`/`copy` copies wholesale into the native Android project. There is no other copy anywhere and no sync step between files — edit files under `public/` directly.

## Commands

There is no build, lint, or test tooling in this repo — `package.json` has no `scripts` block, and there's no test framework or CI config. "Testing" a change means running the app and looking at it.

- **Preview in a browser**: serve `public/` (e.g. `cd public && python3 -m http.server`) and open `index.html`. It talks to a live Firebase project, so it needs network access.
- **Run/build/inspect the Android app**: use the `run-android` skill (`.claude/skills/run-android/driver.sh`), which drives the whole cycle via `adb`/Gradle — `sync` (Capacitor sync), `build` (assembleDebug), `boot`, `install`, `launch`, `screenshot`, `tap`, `text`, `logcat`, `stop`. Run `driver.sh sync` before `driver.sh build` whenever anything under `public/` changed. See the skill's own docs for known gotchas (adb can't type Hangul, focus-vs-rendered timing, an emulator stylus-tutorial overlay, etc.).
- `android/` is a generated Capacitor project — treat it as build output, not hand-written source; native changes go through `npx cap sync android`, not manual edits to `android/app/src/main/assets`. The one hand-maintained exception is `android/app/src/main/java/com/wwscj/weeklyplanner/MainActivity.java` — `cap sync` never touches native Java/Kotlin source under `src/main/java`, so it's safe to customize directly. It currently registers an `OnBackPressedCallback` so the hardware/gesture back action goes to the WebView's own history (`canGoBack()`/`goBack()`) before falling through to the default finish-the-activity behavior — without it, Capacitor core alone (no `@capacitor/app` plugin installed) doesn't route the back action into the WebView at all, so any JS-side `history.pushState`/`popstate` handling (e.g. the checklist modal closing on back instead of exiting the app) would never run. Note the legacy `Activity.onBackPressed()` override doesn't work on this project's androidx.activity version — it's bypassed by the dispatcher — hence the callback-based API.

## Architecture

- **Data model**: Firestore, one document per calendar week at `users/{uid}/weeklyPlanner/{weekKey}`, where `uid` is the signed-in account and `weekKey` is that week's Monday as `YYYY-MM-DD` (`toKey(getMonday(date))`). Each doc holds a single `tasks` array covering all 7 days — there is no one-doc-per-task structure. A task looks like:
  ```js
  { id, day, text, done, order?, createdAt, carriedOver?, forwarded?, originDate?, checklist? }
  ```
  `day` is an **index 0–6 (Mon–Sun) within that week's document**, not an absolute date — the same weekday index means something different in every week's doc. `order` is a manually-assigned sequence number (see the reorder bullet below); tasks predating it just don't have it. `checklist` is an optional array of sub-items, `[{ id, text, done }]` — see the checklist bullet below.
- **Writes are transactional whole-array rewrites**: every change to the current week goes through `mutate(fn)` (in `useWeeklyTasks.js`), where `fn` maps a tasks array to the next one (or `null` for "nothing to do"). `mutate` applies `fn` to local state right away (optimistic UI; `onSnapshot` confirms) and separately calls `WeeklyPlannerAPI.updateWeek(uid, weekKey, fn)` (in `firestoreApi.js`), which runs `fn` against the server's *latest* array inside a `runTransaction` and `.set()`s the result. There's still no per-task Firestore write path — the whole `tasks` array is rewritten every time — but because it's derived from the server's copy rather than this client's possibly-stale one, a write can't wipe changes made meanwhile by another device or by the concurrent last-week carry-over transaction. So `fn` must be **pure** (the transaction may retry it) and must express the change relative to its argument, never close over `tasks`; anything non-deterministic (`uid()`, `Date.now()`) is generated outside `fn`, and toggles compute their new value from what the user saw (`done = !target.done`) rather than re-flipping the server's value. Trade-off: Firestore transactions need a network connection, so edits fail (→ `connectionOk` false) while offline instead of being queued. Additionally, `mutate()` and the same-week carry-over refuse to run unless `tasksReady` — i.e. the local `tasks` array was actually loaded from the doc currently being viewed (`tasksSource === `${uid}/${weekKey}``). Right after a week or account switch, `weekKey`/`authUser` already point at the new doc while `tasks` still holds the previous doc's array until the new snapshot arrives; writing in that window used to overwrite the new week's doc with the old week's tasks (e.g. viewing next week, then tapping 오늘, wiped this week's tasks).
- **Reads are a live subscription** to only the currently-viewed week's doc (`onSnapshot`, keyed by `weekKey` + `authUser.uid`); switching weeks (`weekOffset`) re-subscribes. The one exception is the calendar picker's per-date markers: whenever it opens or flips month, `fetchCalendarMarks` (hook) does a one-shot `fetchWeeksInRange` document-id range query over that month's week docs (keys sort chronologically as strings) and marks each date `open` (some task undone and not `forwarded`) or `done` (dot rendered dark vs. faint); the currently-viewed week uses the live `tasks` instead of the fetched copy.
- **Editing a task** (task menu → 수정) opens `<EditTaskModal>` (`editingId` state in `WeeklyPlanner.jsx`, closed by 취소/X/backdrop or the hardware back button, same `pushState`/`popstate` pattern as the other modals) where both its text and its date can be changed, via `editTask(id, text, targetDate?)` in `useWeeklyTasks.js`. The date (picked from an inline `CalendarGrid`, not a native `<input type="date">`, so it matches the header calendar) is seeded from the task's current absolute date (`weekDates[selectedDay]`, since every task in the current day panel shares that date); nothing is written until 저장. Where the new date lands determines the write path: same day → no-op beyond the text change; a different day *within the currently-open week* → plain `mutate()` with an updated `day`; a date in a **different week** → `WeeklyPlannerAPI.moveTaskAcrossWeeks` (a second Firestore transaction helper, structurally identical to the carry-over one) reads both week docs and atomically removes the task from the source doc while appending it to the target doc, since moving across weeks means moving across two separate Firestore documents. The task optimistically disappears from the current view immediately in that case; the target week only reflects it once it's actually viewed (no cross-week subscription).
- **Auth** is email/password Firebase Auth, one account per person, no auto sign-in of any kind — `WeeklyPlanner.jsx` renders `<AuthScreen>` until `authUser` exists. Signing in on a new device reaches the same `users/{uid}/...` data (Firebase Auth session persists locally per device via the SDK's default IndexedDB persistence, so a signed-in device stays signed in across restarts without needing to log in again). There used to be a single shared anonymous identity everyone used (see `weeklyPlanner/{weekKey}`, pre-account data) — that collection is untouched, unreadable by the app now, and **not** migrated into any account automatically; it's effectively frozen/abandoned.
- **Firestore security rules** live in `firestore.rules` (deployed with `firebase deploy --only firestore:rules`, *not* automatically — remember to redeploy after editing them) and are the actual enforcement point for per-account privacy: `users/{uid}/weeklyPlanner/{weekKey}` allows read/write only when `request.auth.uid == uid`; everything else (including the old shared `weeklyPlanner` collection) is denied by default, since Firestore rules deny anything not explicitly matched.
- **Carry-over**: incomplete tasks left on a past day get copied forward to today automatically (not moved) — the original stays put and is flagged `forwarded: true` so it isn't copied again, while a new independent task (`carriedOver: true`) appears on today, cascading forward day by day until completed. Same-week carry-over is a `mutate()` whose `fn` re-selects the tasks to forward from the server's copy (so two devices opening at once can't both forward the same task); carrying over from *last* week's doc into this week's doc is a Firestore `runTransaction` (reads both docs, writes both) since it spans two documents. Only one week back is checked, not the full history. Each copy carries an `originDate` (`M.D` string, from `formatMD`) inherited from its source and shown as a badge next to the task text — it's set once from the *first* task in the chain and passed through unchanged on every subsequent cascade, so it always reflects the original registration date, not the most recent carry date. Copies created before this field existed have no `originDate` and just render without a badge (`{t.carriedOver && t.originDate && ...}`) rather than showing one blank.
- **Manual ordering**: within a day, tasks sort by done-status first (done always sinks to the bottom, automatic and not overridable) then by `order` ascending (falling back to `createdAt` if unset) — see `tasksFor` in `useWeeklyTasks.js`. There's no "important"/star feature; it was removed because it conflicted with manual ordering. The "순서변경" toggle button in the day panel header puts that day's list into a reorder-only mode (rows collapse to a grip handle + text; check/edit/delete and the add-row are hidden) where tasks can be dragged via native Pointer Events (no drag library) to a new position; dropping calls `reorderDay(dayIdx, orderedIds)`, which persists sequential `order` values for just that day. Switching days auto-exits reorder mode. Dragging a done task above undone ones is visually allowed but snaps back on the next render (done-status grouping still wins) — expected, not a bug.
- **Per-task checklist**: each task can carry its own detail checklist (`task.checklist`, `[{id, text, done}]`), independent of the task's own `done` state — completing every sub-item does **not** auto-complete the parent task, by design. Mutated via `addChecklistItem`/`toggleChecklistItem`/`removeChecklistItem`/`editChecklistItem(taskId, ...)` in `useWeeklyTasks.js`, same `mutate()` pattern as everything else, just reaching one level deeper into the specific task. Each sub-item's text can be edited in place (pencil icon → inline input, same `editingChecklistItemId`/commit-on-blur-or-Enter pattern as editing a task's own text). The `ListChecks` icon on a task opens a modal dialog (`checklistOpenId` state in `WeeklyPlanner.jsx`, one task's modal open at a time) showing the sub-items plus an add-row, closed via its own X button or by tapping the backdrop; a small "`done`/`total`" badge appears next to the task text once it has any checklist items. Carry-over (`makeCarriedCopy`) clones the checklist onto the new copy so in-progress sub-items aren't lost when a task rolls to today.
- **Memos** live in a separate collection, one doc per memo at `users/{uid}/memos/{memoId}` (`{ text, createdAt, updatedAt }`, client-side ms timestamps so a fresh write sorts correctly before the server confirms). Unlike week docs, a memo is only ever written whole by the device editing it, so writes are plain `add`/`update`/`delete` — no transactions, which also means memo edits queue offline instead of failing. `firestore.rules` has a matching owner-only rule.
- **Date/week helpers** (`getMonday`, `addDays`, `toKey`, `formatMD`, `isSameDay`) underpin all of the above — read these first when touching anything date-related.
- All user-facing strings are Korean; match the existing tone/phrasing when adding UI text.
